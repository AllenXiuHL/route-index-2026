洞察

ANALYSIS
120 km/h = 33.3 m/s · 200 ms ≈ 6.7 m

时延的计价单位是米，不是毫秒

把 200ms 换成位移：以 120km/h 行驶，200ms 决策延迟等于 6.7 米的盲区；叠加 100→0 km/h 约 35–40 米的制动距离，系统级安全距离落在 42–47 米。这意味着单芯片方案要成立，必须把感知-预测-规划压进一次前向，任何串行专家都在吃安全余量。“比肩 200-500 TOPS”若不给场景与对照，这 6.7 米就无法被第三方复算。

42.7 ÷ 0.279 ≈ 153 万 · 元戎 6.21 万 ≈ 14.5% 份额

42.7 万台 / 27.9% 反推出一个约 153 万台的月盘子

这个反推说明城区 NOA 已经从旗舰配置变成主流选装，商业逻辑随之改变：既然是新车的常规配置，主控 BOM 就撑不起 500 TOPS，100-200 TOPS 成为主战场不是技术退让，而是成本结构的必然。元戎 8 月 6.21 万台约占大盘 14.5%，第二名的意义在于它用更低的算力带守住了份额。

MPCI 曲线“仅为示意图、未标自家实测值”

TOPS 失效的根因：有效算力不可见

同峰值算力下，内存带宽、算子融合、稀疏化决定实际吞吐，所以行业转向 MPCI（关键接管间隔里程）与“泛化用时”。但一个指标要能当采购依据，至少需要四件事：固定路线集、可复核的接管定义、公开的分母里程、置信区间。缺任何一项，指标就只是叙事——这也是“可审计”比“可炫耀”更难的地方。

洞察

ANALYSIS
LIBERO 98.5%+ · 继续刷分的信息量趋近 0

98.5% 是评测饱和，不是能力饱和

当基准成功率贴近评测方差，排行榜上再涨 0.3 个点已经不可区分。真正有信息量的是“10 分钟长任务的累计成功率”——它会把每一次误差累积都算进去。世界模型被引入的本质，是把误差累积从执行期前移到想象期：先在 6 秒的未来里试错，再决定动不动。

1000 台 × 10 h/天 × 300 天 = 300 万 h/年 · 补 3000 万 h 需 10 年

50 万小时 vs 数千万小时：靠采样补不上

按 1000 台机器人、每天 10 小时、一年 300 天算，一年只能产生 300 万小时真机数据；要从 50 万小时补到 3000 万小时，需要十年。这就是“仿真合成 + 部署后学习”不是选修课的原因：数据缺口 >99% 时，唯一可扩展的变量是单位数据的复用次数，而不是采集人数。

3.0× 提升 · 5 天收敛 · n=1 场景

28.6%→85.7% 的价值在“首日不需要人工示范”

若每台新机都要工程师现场示教，第 1000 台的边际成本不会下降。Physical RSI 把“修复”变成可复用资产，改的是成本曲线而不是单点指标。但证据强度必须说清楚：这是单场景、单机型的观测，第三方尚未复现，属于强信号、弱证据。

ANALYSIS
HarnessFix：SWE-bench Verified / Terminal-Bench 2.0 / GAIA / AppWorld

同一模型，换个 Harness 差 15.2%–50.0%

这条数字最直接的用途不是“又一个 SOTA”，而是说明模型排行榜不能预测生产表现。团队在做技术选型时，应该把 Harness 版本（工具集、上下文策略、权限模型）写进评测口径，否则同一模型的两份测评结果根本不可比——这也是“Agent 工程”第一次有了类似“硬件配置”的东西。

n = 500，p ≈ 0.5 时 95% CI ≈ ±4.4 个百分点

500 题上的 1-2 个点不显著

SWE-bench Verified 的 500 道题，决定了榜首几名之间的差距很可能只是抽样噪声。按二项分布算，±4.4 个百分点的置信区间意味着：真正值得看的是失败模式分布（改错文件、跳过测试、上下文溢出），而不是总分小数位。这也解释了为什么 HarnessTester 这类“测试充分性”工作比刷榜更有价值。

隐藏率 72% · bug 密度高于模型缺陷密度

122 个 bug 里 88 个先前未知

如果 122 个真实 Harness bug 中有 88 个此前未被发现，说明这类缺陷既不在 benchmark 里，也不在团队的回归测试里。这就是“Agent = Model + Harness”的工程含义：可靠性预算应该按 Harness 的复杂度分配，而不是按模型参数量分配。

关键分歧

框架选型已不再是真正的难题，分水岭在于 Agent 的可靠性该靠“更好的模型”还是“更好的 Harness 工程与测试”——HarnessFix / HarnessTester 押注后者，但只在软件 Agent 场景验证；具身“物理试错代价高、失败不可回滚”，让 Harness 层的容错难一个量级。

CROSS-CUTTING

三条线，其实在答同一道题

把三个方向并排放，会发现它们在同一年做同一件事：把叙事从“模型有多强”换成“系统失败时能不能被定位、被复现、被修复”。

方向主要瓶颈可审计指标仍然缺什么
自动驾驶BOM 与长尾场景接管间隔里程（MPCI）公开分母 + 统一接管定义
具身真机数据与长时程长任务成功率、首日成功率统一评测标尺 + 第三方复现
AgentHarness 可靠性失败归因率、Harness bug 数具身场景的容错与回滚机制

三条线在同一时间点做同一件事

2026 年三个方向的公开叙事都从“模型能力”转向“系统可靠性”：车看接管里程、机器人看长任务成功率、Agent 看 Harness 修复率。指标不同，但都在回答“这个系统失败时，我能不能定位、能不能复现、能不能修”。

共同的缺口是可审计的分母

接管里程缺公开里程数，长任务成功率缺统一任务集，Harness 修复率缺 Harness 版本号。没有分母，就没有可比较的分子——这是三个方向共同的“基础设施债”。

成本约束的形状完全不同

自动驾驶是 BOM 约束（100-200 TOPS 的车规芯片），具身是数据约束（50 万小时对几千万小时），Agent 是评测约束（500 题对长程任务）。所以跨方向抄方案会失效，能抄的是“失败数据闭环”这一层方法论。

Agent · 系统开发者

先看什么
先读 03 的 Harness 五件事与 500 题置信区间，再看框架对比表的“风险”列。
押注什么
押“可观测 + 可测试的 Harness”——轨迹归因、测试生成、熔断审计，而不是押框架本身。
别踩什么
别把框架当护城河（迁移成本在状态持久化，不在 API）；别用总分小数位做技术判断。
